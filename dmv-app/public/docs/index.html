IBM Digital Credentials // DMV App API

This is documentation for the DMV App, and the workflow of adding credentials to your profile. This uses a layered approach, the front end never directly calls IBM backend, instead it's masked through a proxy. The UI calls proxy, which handled calling IBM infrastructure on the server.

System Responsibilities

Frontend / React application

  • Starts login with /auth/login and creates offers with /credentials/offers.
  • Does not hold OIDC client secrets or agent tokens.

Express server / proxy layer

  • Serves the frontend and runs the auth and credential routes.
  • Keeps req.session.user for browser auth.
  • Also keeps a separate DMV Agent token for issuing credentials upstream.

Upstream backend / IBM Verify + Diagency

  • IBM Verify handles user sign-in.
  • Diagency creates and manages the credential offers. Server side.
  • Returns the login details, offer state, and QR data the app needs.

OIDC Authentication Routes

GET /auth/login

Overview: Initialises the OpenID Connect PKCE authorisation flow.

Backend Flow: The server loads OIDC metadata, derives a PKCE code_verifier, computes the code_challenge, generates a state, and stores those values in the in-memory authParams map. It then returns an authUrl for the React frontend to use as the redirect destination.

POST /auth/callback

Overview: Consumes the IBM Verify authorisation code exchange.

Backend Flow: The server validates the incoming state, recovers the stored PKCE verifier, exchanges the authorisation code at /oauth2/token, optionally calls /oauth2/userinfo, and hydrates req.session.user with authenticated state, tokens, login time, and user claims.

GET /auth/status

Overview: Reports the current browser session's authentication state.

Backend Flow: Reads req.session.user.authenticated and returns the authenticated flag with user metadata when available. This allows frontend route guards to decide whether to render /profile or redirect back to login.

POST /auth/logout

Overview: Destroys the local authenticated session.

Backend Flow: If an id_token exists, the server builds an OIDC end-session URL. It then destroys the Express session and returns a logout response the frontend can safely consume.

Session & Guard Model

  • Cookie name: dmv.session.id.
  • req.session.user stores the login state and token expiry details.
  • requireValidSession blocks all issuance routes if the session is missing or expired.

Verifiable Credential Issuance Routes

All paths mapping to /credentials/* require a valid OIDC-authenticated browser session. Once the browser session is authorised, the server separately uses the DMV Agent's client_credentials token for Diagency requests.

POST /credentials/offers

Overview: Provisions a Verifiable Credential Offer, typically an mDL issuance offer.

Frontend Caller: VciCredentialService.createCredentialOffer() from ProfilePage.tsx.

Backend Flow: The frontend builds the payload from profile data, then the server proxies POST /v1.0/oidvc/vci/offers upstream using the DMV Agent token. This keeps Diagency credentials out of the browser.

GET /credentials/offers/:id

Overview: Retrieves either QR code content or the JSON status for a specific offer.

Frontend Caller: VciCredentialService.fetchOfferImage() and VciCredentialService.checkOfferState().

Backend Flow: The server validates :id with uuid.validate(id) before forwarding GET /v1.0/oidvc/vci/offers/:id upstream. This reduces arbitrary path abuse and ensures only recognised offer identifiers are proxied.

End-to-End Issuance Flow

  1. 1The user opens the DMV app and clicks Sign in with IBM Verify.
  2. 2AuthProvider.tsx calls /auth/login and redirects the browser to the provider.
  3. 3The provider redirects back to /logincallback.
  4. 4OidcCallback.tsx calls /auth/callback, and the server creates req.session.user.
  5. 5The user lands on /profile and starts the licence offer flow.
  6. 6VciCredentialService.ts maps the profile data and posts it to /credentials/offers.
  7. 7The proxy sends the request upstream and returns the offer payload to the frontend.
  8. 8The frontend fetches the QR image and keeps polling /credentials/offers/:id until the offer state changes.
