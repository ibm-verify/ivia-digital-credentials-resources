IBM Digital Credentials // Bank App API

Ok, so documentation for API across the bank app. There is a layered approach. Quick notes: All api routes go through a proxy. This means the front end never actually calls IBM api's directly, they always call their own proxy which passes the requests through.

System Responsibilities

Frontend / React application

  • Only calls local endpoints like /credentials/verifiable/presentation.
  • Does not talk to Diagency directly or hold secrets.

Express server / proxy layer

  • Serves the frontend and handles the local API routes.
  • Gets the Bank Agent token with client_credentials.
  • Stores the current exchange in req.session.dcRes. If exchanges exist, delete to ensure single source of truth and multiple sessions don't get stored.

Upstream backend / IBM Diagency

  • Creates and manages the presentation exchange. This is IBM infrastructure.
  • Returns the live exchange state and the final verified data. This gets passed back through the proxy to the frontend.
  • The real exchange state lives SERVER SIDE (very important!), not in the browser.

Runtime Configuration & Session Model

Express session state

  • Cookie name: bank.session.id.
  • The server keeps the latest exchange response in req.session.dcRes. It will delete any existing to remove duplicates
  • The important bit is the SERVER SIDE exchange id, because that is what later requests use.

What the main functions do

  • setupProxy: sets up body parsing, sessions, logging, and the /credentials router.
  • getOrRefreshBankToken: gets or reuses the Bank Agent token used for upstream calls.
  • preCallDigitalCredsService: builds the target URL, adds the bearer token, and prepares the upstream request.
  • callDigitalCredsService: actually sends the fetch request to Diagency and normalises the response into status, headers, json, data, or buffer.
  • sendDigitalCredsResult: takes that normalised result and sends it back to the browser.

Proxy Routes & Endpoints

POST /credentials/verifiable/presentation

What it does: Starts a new presentation exchange, or clears the old one first if the session already has one.

Server call: POST /v1.0/oidvc/vp/exchange, and sometimes DELETE /v1.0/oidvc/vp/exchange/:id first (If exists already).

  • The route handler works out whether there is already an active exchange in req.session.dcRes.
  • If there is one, it deletes the old exchange first.
  • It then creates a new exchange and stores the response in the session.
  • The browser gets back the wallet engagement data it needs for the QR step.
GET /credentials/verifiable/presentation

What it does: Polls the current presentation exchange.

Upstream call: GET /v1.0/oidvc/vp/exchange/:id.

  • The route reads the exchange id from req.session.dcRes.
  • The proxy calls Diagency for the latest exchange state. This is where it verifies using IBM software
  • The updated response is written back into the session.
  • The browser gets the latest execution_state and related data.

GET /credentials/verifiable/presentation/vc

What it does: Gets the final verified attributes after the presentation succeeds.

Upstream call: GET /v1.0/diagency/verifications/:id.

  • The route uses the exchange id already stored in the session.
  • The proxy fetches the verification result from Diagency.
  • Only the decoded attributes are passed back to the browser.
  • This keeps the frontend payload small and focused on what the form actually needs.

Main functions involved: preCallDigitalCredsService, callDigitalCredsService, sendDigitalCredsResult.

End-to-End Verification Flow

  1. 1The user opens /signup and starts the bank account flow.
  2. 2The frontend calls POST /credentials/verifiable/presentation to create an exchange.
  3. 3The proxy stores the upstream response in req.session.dcRes and sends back the wallet engagement data.
  4. 4The frontend shows a QR code or wallet link from that response.
  5. 5The frontend polls GET /credentials/verifiable/presentation until the exchange finishes.
  6. 6When it succeeds, the frontend calls GET /credentials/verifiable/presentation/vc to get the verified attributes.
  7. 7Those attributes are mapped into the signup form so the user can carry on.
